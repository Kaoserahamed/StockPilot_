# Dependencies

Which manifests are authoritative, what the current major lines are, and how to
audit freshness. The point of this file is that a reviewer can answer "is this
out of date?" **without re-running a scan** — the tables below are the snapshot,
and the commands are how to check whether it has drifted.

## Which file is the source of truth

Both stacks are fully pinned and both lockfiles are committed, so a fresh clone
reproduces the same dependency closure.

| Stack | Authoritative declaration | Lockfile | Generated by |
|-------|---------------------------|----------|-------------|
| Backend | `backend/pyproject.toml` → `[project].dependencies` | `backend/uv.lock` | `uv lock` |
| Backend (pip) | `backend/requirements.txt` | `backend/requirements.lock` | `python backend/scripts/generate_lockfile.py` |
| Backend dev/CI | `backend/requirements-dev.txt` | `backend/requirements-dev.lock` | `python backend/scripts/generate_lockfile.py` |
| Frontend | `frontend/package.json` | `frontend/package-lock.json` | `npm install --package-lock-only` |

`pyproject.toml` and `requirements.txt` must stay in lockstep — that contract is
enforced by `backend/tests/test_dependency_manifests.py`, which fails if a pin
appears in one manifest but not the other or in `uv.lock`. Add a dependency to
**both** files, then regenerate all three lockfiles in one commit.

## Auditing freshness

Run these when you want to know whether the tables above have drifted. The CI
jobs that do the same checks are `backend-audit`, `frontend-audit`,
`backend-lock-drift`, and `backend-reproducible-install`.

```bash
# Backend: is anything in the declared manifest behind the latest release?
cd backend && pip list --outdated -r requirements.txt

# Backend: list the direct (non-transitive) installs actually present in the
# venv, and reconcile them with the "Backend runtime pins" / "dev/CI pins"
# tables above. Expect a small, explainable delta:
#   - `httptools`, `watchfiles`, `websockets` come from the `uvicorn[standard]`
#     extra, and `grpcio-status` from `google-generativeai` - extras, not top-level
#     declares, so they appear here but not in the tables.
#   - `pydantic`, `SQLAlchemy`, `PyYAML`, `pytest` are shown as "required" (not
#     listed) because another declared package depends on them; they are still
#     first-class pins in requirements.txt and appear in the tables.
# Anything else that shows up here should be traceable to requirements*.txt.
cd backend && pip list --not-required --format=freeze

# Frontend: same question for the declared dependencies.
cd frontend && npm outdated

# Do the committed lockfiles still match the manifests?
cd backend && uv lock --check        # pyproject.toml vs uv.lock
cd backend && python scripts/generate_lockfile.py --dev   # regenerates requirements*.lock
cd backend && git diff --exit-code requirements.lock requirements-dev.lock   # empty == in sync
cd frontend && npm ci                # exits non-zero if package-lock.json drifts

# Are any of the locked packages affected by known advisories?
cd backend && pip-audit -r requirements.lock
cd frontend && npm audit --omit=dev
```

The lockfile generator has no `--check` mode: run it, then let `git diff --exit-code`
tell you whether the committed lockfiles were already up to date. The same
agreement is asserted in Python by `backend/tests/test_dependency_manifests.py`,
so a forgotten half-edit is caught by `backend-test` too.

The `[project].dependencies` table in `backend/pyproject.toml` mirrors
`requirements.txt`, so tooling that introspects PEP 621 metadata (`pip show`,
`uv`, scanners) can count the direct runtime deps directly rather than inferring
them. The `pip list --not-required` command above is the runtime counterpart: it
shows what is actually installed as a top-level package in a built venv, which
is how to confirm the documented tables still match reality (last reconciled:
every documented pin present at its documented version; the only extras were the
`uvicorn[standard]` and `google-generativeai` transitive pulls noted inline).

## Update policy

- **Patches and minors:** land them as small, single-purpose commits through
  Dependabot's PRs, and regenerate the lockfiles in the same commit.
  Dependabot's config is `.github/dependabot.yml`.
- **Majors** (e.g. `next` 14 → 15, `react` 18 → 19, `SQLAlchemy` 2 → 3, `fastapi`
  0.x → 1.0): these change contracts. Open a PR of their own, note the migration
  in [`../CHANGELOG.md`](../CHANGELOG.md), and if the reasoning is worth keeping,
  add an ADR under [`architecture/decisions/`](architecture/decisions/).
- Keep `react` and `react-dom` on the same version, and keep `next` exactly
  pinned — an accidental caret there lets a clone install a Next line the app has
  never been tested against.
- Bump this file's tables in the same commit as the pin, or the snapshot becomes
  the thing that is stale.
